# ordinary_form_rlm.py

Версия 0.6.5. Автономный Python-скрипт читает обычные формы 1С из `Form.bin` и создаёт представление для индексации [rlm-tools-bsl](https://github.com/Dach-Coin/rlm-tools-bsl):

```text
Form.xml
Form\Module.bsl
```

> Скрипт не изменяет `Form.bin` и использует только стандартную библиотеку Python. Для работы копируйте коллегам всю папку: скрипт, словарь событий, `README.html`, `AUTHORS.md` и `LICENSE`.

## Что переносится в Form.xml

Элементы распознаются по GUID бинарной записи. В том числе отдельно распознаётся `PictureDecoration`, поэтому его обработчик нажатия не попадает в события содержащей его панели. Для `Panel` сохраняются все страницы, включая пустые. Принадлежность элемента странице берётся из индекса страницы в layout-записи `Form.bin`; элементы без такого индекса остаются непосредственными дочерними элементами панели.

Собственные действия кнопок `CommandBar`, в том числе во вложенных группах, попадают в `Commands`. Имя кнопки связывается с записью действия по UUID, а обработчик берётся только из бинарной записи. Встроенные команды платформы без BSL-обработчика в `Commands` не добавляются.

## Требования

- Python 3.10 или новее; рекомендуется Python 3.11.
- Для Git-aware инкрементального режима команда `git` должна быть доступна в `PATH`.
- Установка пакетов через `pip` не требуется.

## Проверка

Откройте PowerShell в папке со скриптом:

```text
python .\ordinary_form_rlm.py --version
python .\ordinary_form_rlm.py --help
```

## Одна форма

Все пути ниже — примеры. В `--output` указывается каталог формы, а не имя файла `Form.xml`.

```text
python .\ordinary_form_rlm.py `
  "C:\Work\workspace\projects\DemoProject\src\cf\Documents\ПримерДокумента\Forms\ОсновнаяФорма\Ext\Form.bin" `
  --output "C:\Work\output\ОсновнаяФорма\Ext"
```

Результат появится в `C:\Work\output\ОсновнаяФорма\Ext\Form.xml` и `C:\Work\output\ОсновнаяФорма\Ext\Form\Module.bsl`.

## Дерево конфигурации

Для обработки всех `Form.bin` ниже заданного каталога добавьте `--recursive`. Структура подкаталогов сохраняется:

```text
python .\ordinary_form_rlm.py `
  "C:\Work\workspace\projects\DemoProject\src\cf" `
  --output "C:\Work\output\DemoProject-forms" `
  --recursive `
  --verbose
```

Для каталога `src\cf` внутри проекта с `project.toml` корень определяется автоматически. Карта событий хранится в проекте. Каталог вне `src\cf` обрабатывается как самостоятельный источник: его карта и диагностика сохраняются в `ordinary-forms` внутри указанного каталога, а существующая проектная карта только читается как дополнительный источник соответствий.

```text
python .\ordinary_form_rlm.py `
  "C:\Work\exports\DemoProject\src\cf" `
  --output "C:\Work\output\DemoProject-forms" `
  --project-root "C:\Work\exports\DemoProject" `
  --recursive
```

## Внешние обработки и отчёты

Укажите непосредственно каталог внешней обработки или отчёта. Наличие `src\cf` для него не требуется; вложенные каталоги выгрузки находятся рекурсивно.

```text
python .\ordinary_form_rlm.py `
  "C:\Work\workspace\projects\DemoProject\src\epf\ExampleProcessor" `
  --output "C:\Work\workspace\projects\DemoProject\src\epf\ExampleProcessor" `
  --recursive --full --verbose
```

Для внешнего отчёта или обработки укажите её каталог с `--recursive` и передайте тот же каталог в `--output`, чтобы `Form.xml` создавался рядом с каждым `Form.bin`. Командный файл для запуска можно создать в собственном рабочем проекте.

Чтобы использовать соответствия событий, уже полученные при разборе `src\cf`, добавьте `--ordinary-forms "C:\Work\workspace\projects\DemoProject\ordinary-forms"`. Параметр принимает именно каталог, содержащий `event-map.json`. Явная карта имеет приоритет над локальной картой внешней обработки и только читается. Локальная карта остаётся в каталоге внешней обработки; `unresolved-events.json` появляется там только при необходимости ручного сопоставления. Если указанной карты нет, запуск завершается ошибкой.

## События обычных форм

В скрипте нет встроенной таблицы соответствий числовых ID событиям. Соответствия строятся отдельно для конкретного проекта по его собственным `Form.bin`. Файл `ordinary-form-events.json` содержит редактируемый словарь допустимых имён событий обычных форм, элементов и расширений. Пользователь может исправлять и дополнять его под свои формы; полнота и точность исходного списка не гарантируются. Автономный разборщик читает этот файл рядом со скриптом; встроенному разборщику после правки исходного JSON нужна повторная сборка и установка. Словарь проверяет и нормализует имя кандидата, но не назначает ID без статистики проекта. Результат хранится рядом с проектом:

- `<project-root>\ordinary-forms\event-map.json` — принятые статистические и ручные соответствия;
- `<project-root>\ordinary-forms\unresolved-events.json` — только если есть события для ручного сопоставления.

### 1. Сбор наблюдений

Анализатор читает события формы и всех элементов каждой формы. Каждое найденное назначение обработчика является отдельным наблюдением. Наблюдения группируются по паре:

```text
ТипЭлемента + IDСобытия
```

Например, `InputField / 2147483647` и `ChoiceField / 2147483647` являются разными группами. Для таблицы ключ дополняется GUID расширения и имеет вид `Table@<guid> / ID`, поэтому одинаковый номер у дерева и списка объектов не смешивается. Несколько элементов одной формы дают несколько голосов, но требование по количеству разных форм считается отдельно.

### 2. Проверка существования обработчика

Наблюдение участвует в анализе только тогда, когда в модуле формы найдено соответствующее объявление процедуры или функции. Распознаются в том числе многострочные объявления. Записи без найденной процедуры не голосуют, не влияют на confidence и учитываются отдельно как `ignored_no_procedure`. Группа, целиком состоящая из таких записей, не требует ручной классификации и попадает в `ignored_no_procedure_groups`.

### 3. Формирование допустимого голоса

| Источник | Правило | Пример |
| --- | --- | --- |
| Direct | Имя обработчика начинается с полного имени элемента; остаток нормализуется по самому длинному допустимому событию этого типа элемента. | `КонтрагентПриИзменении` и ошибочное `КонтрагентаПриИзменении` дают `ПриИзменении`, если полное имя элемента — `Контрагент`. |
| Known suffix | Если direct не сработал, выбирается самое длинное имя события данного типа из словаря, ручных правил и уже подтверждённой карты проекта, которым заканчивается handler. | `ПолеНачалоПеретаскивания` выбирает `НачалоПеретаскивания`, а не короткое `Перетаскивание`. |
| Inferred suffix | Для разных handler-имён одной группы вычисляется самый длинный общий суффикс, после чего он обязательно нормализуется по словарю событий типа элемента. | `ФильтрыПисемПриАктивизацииКолонки` и `ТоварыИУслугиПриАктивизацииКолонки` → `ПриАктивизацииКолонки`. |
| Сама форма | Полное имя обработчика даёт голос, только если оно есть в словаре событий формы. | `ПередЗакрытием` даёт голос за `ПередЗакрытием`. |

Источники проверяются именно в этом порядке. Словарь привязан к типу элемента: например, `Выбор` допустим для `Table`, но не для `Panel`. Полностью одинаковое произвольное имя handler, сколько бы раз оно ни повторялось, само по себе не образует inferred suffix: нужны разные handler-имена.

Тип владельца берётся из GUID записи элемента. Разборщик распознаёт в том числе поле табличного и HTML-документа, календарь, полосу регулирования, диаграмму и диаграмму Ганта, поэтому их события не приписываются содержащей их панели. Для таблицы статистический ключ включает GUID расширения и записывается как `Table@<guid>`: это разделяет одинаковые ID с разным смыслом у дерева, списка объектов и других разновидностей таблицы. В создаваемом `Form.xml` элемент при этом остаётся обычным `Table`.

Несколько элементов могут ссылаться на один handler — это нормальная ситуация. Если хотя бы одна ссылка явно подтверждает допустимое имя события либо оно распознано по известному суффиксу, остальные ссылки на тот же handler дают тот же голос при отсутствии противоречия.

### 4. Принятие кандидата

| Ситуация | Решение |
| --- | --- |
| Есть ровно один кандидат и хотя бы один допустимый голос | Кандидат принимается как единогласный независимо от количества голосов и форм. |
| Есть несколько кандидатов | Победителю одновременно нужны минимум 5 голосов, не менее 80% допустимых голосов и подтверждения минимум в 3 разных формах. |
| Нет допустимых голосов | ID остаётся нерешённым. |
| Большинство не достигло одного из порогов | ID остаётся нерешённым вместе со всеми кандидатами и примерами. |

Доля рассчитывается только по допустимым кандидатам:

```text
ДоляПобедителя = ГолосаПобедителя / ВсеДопустимыеГолоса
```

### 5. Сигнатуры и mixed semantics

Сигнатура нормализуется без имени процедуры, регистра, пробелов, `Знач` и значений по умолчанию, но с сохранением порядка параметров. Она не определяет имя события самостоятельно, а помогает отличить статистический шум от разных семантик.

Если в одной группе устойчиво присутствуют разные suffix-кандидаты вместе с различающимися кластерами сигнатур либо несколько конфликтующих direct-кандидатов, устанавливается `mixed_semantics = true`. Такая группа не получает автоматическое соответствие даже при формальном большинстве. Ручной ответ сохраняется в диагностике со статусом `manual_with_mixed_semantics`, но не распространяется на всю неоднородную группу.

### 6. Защита от конфликтов ID

Внутри одного типа элемента одно имя события не назначается автоматически нескольким ID. Если несколько ID претендуют на одинаковое имя:

1. ручное соответствие имеет абсолютный приоритет;
2. между статистическими соответствиями побеждает большее количество голосов;
3. при равенстве голосов сравнивается количество разных форм;
4. затем сравнивается доля победителя;
5. при полном равенстве оба ID остаются нерешёнными.

### 7. Примеры решений

| Голоса | Результат |
| --- | --- |
| `ПриИзменении: 1` | Принято единогласно. |
| `ПриИзменении: 8`, `ПриАктивации: 2`, не менее 3 форм | `ПриИзменении` принято: 80%. Два меньшинства записаны как выбросы. |
| `ПриИзменении: 7`, `ПриАктивации: 3` | Не принято: только 70%. |
| Четыре единогласных голоса в трёх формах | Принято: для единогласия количественный порог не применяется. |
| Один произвольный handler повторяется 100 раз | Кандидат не создаётся: одинаковые имена не подтверждают смысловой суффикс. |
| Несколько разных handler заканчиваются на `ОбработкаРасшифровки` | Общий суффикс может стать кандидатом и проходит обычные статистические пороги. |
| Под одним ID устойчиво обнаружены разные события и разные сигнатуры | `mixed_semantics`; группа остаётся для проверки независимо от большинства. |
| Два ID типа `Table` единогласно предлагают `ПриАктивизацииСтроки`: 301 голос против 1 | Имя закрепляется за сильным ID; слабый ID остаётся нерешённым из-за конфликта карты. |

### 8. Содержимое файлов

`event-map.json` содержит версию схемы и анализатора, описание политики `voting_policy` и принятые `mappings`. Для статистического правила сохраняются:

- `observations`, `usable_observations`, `ignored_no_procedure`, допустимые и исключённые голоса;
- число голосов победителя, его доля и количество разных форм;
- `raw_direct_candidates`, нормализованные `direct_candidates`, `known_suffix_candidates`, `suffix_candidates` и итоговое распределение `candidate_names`;
- `signature_clusters`, `mixed_semantics` и причины неоднородности;
- способ принятия: `unanimous` или `threshold_majority`.

`unresolved-events.json` создаётся только при непустом массиве `events`. Отсутствие файла означает, что ручное сопоставление не требуется. Если файл создан, в нём доступны:

| Раздел | Что означает | Действие |
| --- | --- | --- |
| `analysis_summary` | Итоговые количества наблюдений, пропусков, принятых кандидатов, нерешённых и mixed-групп. | Помогает оценить объём проверки. |
| `events` | Действительно нерешённые ID с кандидатами, путями, handler и сигнатурами. | Только здесь заполняется `event_name` после проверки в Конфигураторе. |
| `statistical_outliers` | Меньшинство для уже принятого пороговым большинством правила; принятое имя находится в `accepted_event_name`. | Ничего заполнять не нужно. Можно факультативно проверить подозрительное имя handler. |
| `ignored_no_procedure_groups` | Ссылки, для которых в модуле не найдена процедура или функция. | Обычно это старые или оборванные ссылки. Они не голосуют и требуют внимания только при целевом аудите формы. |

> **Если файла нет, разбор завершён без ручной проверки.** Прежний пустой отчёт удаляется при следующем запуске. Диагностические выбросы и ссылки без найденной процедуры сами по себе не создают файл.

### 9. Ручное разрешение

Этот раздел применяется только тогда, когда массив `events` непуст.

1. Откройте `ordinary-forms\unresolved-events.json`.
2. Найдите запись в массиве `events` и форму по `metadata_path`.
3. Проверьте событие в Конфигураторе.
4. Заполните точное имя в поле `event_name`, не меняя `control_type` и `source_id`.
5. Повторите анализ или обычное преобразование.

Заполненное значение переносится в `event-map.json` с источником `manual` и имеет приоритет для однородной группы. Для `mixed_semantics` ответ сохраняется в диагностике, но группа намеренно не считается полностью разрешённой.

### 10. Когда карта пересчитывается

- карта ещё не создана;
- изменилась версия анализатора;
- в `unresolved-events.json` заполнен ручной ответ;
- в изменённых формах появился ID, отсутствующий в карте;
- задан `--full` или `--analyze-events-only`.

Статистические правила при пересчёте строятся заново по текущим `Form.bin`; ручные правила сохраняются. При изменении версии анализатора все производные `Form.xml` автоматически пересобираются один раз, даже если исходные `Form.bin` не менялись.

```text
python .\ordinary_form_rlm.py `
  "C:\Work\workspace\projects\DemoProject\src\cf" `
  --project-root "C:\Work\workspace\projects\DemoProject" `
  --analyze-events-only
```

> Карта относится к конкретному проекту и версии конфигурации. Передавайте коллегам всю автономную папку, а файлы `ordinary-forms` храните в Git соответствующего проекта.

## Инкрементальный и полный режимы

| Режим | Поведение |
| --- | --- |
| По умолчанию | Учитывает изменения Git и время обновления результата; актуальные формы пропускаются. |
| `--full` | Обрабатывает каждую найденную форму независимо от Git и времени файлов. |
| `--verbose` | Показывает строки `OK`, `SKIP` и `ERROR` для отдельных форм. |
| `--analyze-events-only` | Перестраивает карту событий, не создавая `Form.xml`. |

## Итоговый отчёт

После выполнения скрипт печатает JSON. Основные поля:

- `forms_processed` — обработано;
- `forms_skipped` — пропущено как актуальные;
- `forms_failed` — завершилось ошибкой;
- `event_mappings`, `unresolved_events` — размер карты и количество идентификаторов для проверки;
- `attributes`, `controls`, `tables`, `columns`, `commands`, `handlers` — найденные элементы и обработчики.

## Коды завершения

| Код | Значение |
| --- | --- |
| 0 | Все выбранные формы обработаны или корректно пропущены. |
| 1 | Ошибка чтения одиночной формы либо хотя бы одна ошибка в пакетном режиме. |
| 2 | Некорректные параметры командной строки. |

В пакетном режиме подробности сохраняются в поле `forms_failed`; с `--verbose` также выводится путь каждой проблемной формы.
